# 更新不断：传输与长连接所有权、蓝绿换代

> 维护约定文档。改这块之前先读。目标是插件自更新（npm 热更 / OTA 整包）时不掐断手机连接。

## 分层（谁该长命、谁会换）

- **稳定外壳**（以 `lib/index.js` 顺引用算出的集合为准，见 `lib/shell/loaded-files.js`；启动即冻结、改它就要重启 DSH）：
  现在只剩内核与更新机制本身——`lib/shell/*`、`lib/http/routing.js`、`lib/shared/{http-util,paths,private-address}.js`
  （约 20 个文件；`lib/shared/e2ee*.js` 跟着移动端守卫一起挪进了代，见下）。
  - **传输总管** `lib/shell/transport-host.js`：**持有** six 条传输的实例并管它们的提交时切换；
    三条主链路（sidecar / 总控上报 / mux 长连接）的实现住在「代」里，实例由外壳持有、提交时才换。
  - **蓝绿分发表**：`lib/shell/runtime.js`。代注册的路由登记进 staging 表，每个路径在真服务器上
    只挂一个稳定分派器（读 live 表）；提交时原子把 live 指向新代。
- **一代实现**（`lib/impl.js`，可热更换）：业务装配——路由处理器、事件流来源、镜像推送，以及
  **全部线路实现**（三条主链路 + FRP / 隧道助手 / 点对点）与纯计算（服务商清单、地址候选）。
  线路实现代码住代里；主链路以「稳定门面 + 提交时换实例」由外壳托管（见下），换代不换门面引用。

## 换代流程（蓝绿）

1. 装包（后台跑，老一代照常服务，传输一行不动）。
2. 先把新代模块 import 进内存（失败则旧代毫发无损）。
3. 新代 `apply` 注册的路由进 staging（挂稳定分派器），**不立刻上线**。
4. 提交：分发表原子切到新代。
5. 自检（打 `/api/mobile/v1/health`）：不过就按分发表退回旧代、卸新代——旧代一直活着，无空窗。
6. 成功：旧代排空后在飞请求再 `dispose`。

## 维护约束（改之前先看）

- **新增任何传输/常驻连接，必须挂到 `transport-host.js`，不许挂在一代实现的 `apply` 里**。
  挂错了，换代就会把它停掉再重建，用户能感觉到断。
- 传输对外一律用**惰性启动 + providers 注入**：只有「认识该服务」的一代注入来源时才真正 start，
  这样回滚到不认识该服务的旧版时，外壳与旧代不会各起一份（重复 frpc / 重复上报）。
- **新增路由必须走 `ctx.webServer.register` / `registerUpgrade`**（外壳已包成分发），别绕过，
  否则新一代注册会和旧代撞 duplicate route。
- 装配层（`lib/impl.js`）要保持小巧（`test/assembly-layer.test.cjs` 钉着它的代码行数）：业务逻辑住各条线路模块里。
- **线路相关的「纯计算」也不许外壳自己 require**（服务商线路清单、地址候选计算这类）。它们虽然
  不是常驻进程，但改一次就等于改外壳、要重启 DSH。做法跟传输一样：由当前这一代经 providers
  注入进外壳，外壳只转交。已把服务商线路清单、节点小宝识别、地址候选计算这么搬出去
  （`test/shell-boundary.test.cjs` 用前缀 + 点名钉着外壳引用图里不许再出现它们）。私有地址判断
  例外：它抽到 `lib/shared/private-address.js` 仍在外壳里，但它是改动极少的纯谓词，刻意留壳。
- **移动端信封/鉴权守卫（token + 协议 v2）住 `lib/mobile/guarded.js`（代里），外壳不许引**：它原本在
  `lib/http/routing.js` 里，被信封那几件（`lib/shared/e2ee*`）拖着，改一次移动鉴权或信封就得重启 DSH。
  外壳只保留 `localOnly` 需要的最小来源判定与 `sendJson`。`lib/mobile/` 前缀由外壳边界守卫兜着，
  防止它哪天又被搬回外壳、把信封重新冻进去。
- **单实例主链路（中转 sidecar / 总控上报 / mux 长连接）也热换，但走「提交时才换实例」**：实现住
  代里，当前这一代 `adopt` 时把「待建工厂」交给外壳；外壳给一代一个**稳定门面**（方法都委托到当前
  实例）。换代时**不立刻拆旧实例**——运行时确认新代提交成功且自检通过后才 `commit`：停旧、建新、起新；
  换代失败回滚则 `rollback` 只丢弃待建、旧实例一直活着。于是改这三条主链路**不需要重启 DSH**，只在
  提交那一刻短暂重连一次。门面跨实例稳定，是「换代不用换引用」的关键；配置/注册类方法（setProviders、
  onTunnelUp 等）待建期先缓存、提交建新后回放。订阅类方法（`onTunnelUp` / `onRouteAdopted`）在回放时
  把退订凭据一并交回这一代、随它 `dispose` 注销，于是反复同指纹热重载也不会在同一实例上累积订阅。
  `test/transport-host-frp-adopt.test.cjs` 钉着契约。
- **可选线路（FRP / 隧道助手 / 点对点）**：实现住代里，外壳按实现指纹「沿用或重建」——指纹不变沿用
  （不断线），变了只换这一条（短暂重连，DSH 不重启）。

## 已知限制（如实）

- **SSE 事件流**：mux 长连接（手机那条持久 WS）已归外壳、换代不断；但 App 若走 SSE 兜底，
  那条流仍由当前代服务，换代会续传一次（很快，靠 App 的序号/重放兜）。要彻底不断需把 SSE
  的 socket 与事件源也搬进外壳，代价更大，暂未做。
- **传输 worker 自身代码更新**（sidecar worker / 助手进程的代码版本变化）仍需要重开进程；由新的
  sidecar 实例在提交时重新 fork 实现，表现为这条链路短暂重连。
- **改稳定外壳本身仍需重启 DSH**（外壳不热更）。所以外壳里只放「很少变」的内核与更新逻辑。
- **仍会让用户重启一次 DSH 的情况**（要么物理上做不到，要么尚未自动化，动手前先认账）：
  ① 改稳定外壳本身——装载 / 换代分发表 / 传输总管 / 更新编排 / 控制面来源守卫；
  ② **新增一条可选网络线路**——传输总管目前是逐条登记的门面，加线路要改外壳（这是目前最可能
  复发的一条，真要大改可另做通用线路登记表）；
  ③ DSH 宿主升级改了插件 / 路由 / 服务的接口约定（外壳那层适配要跟着改，能通用的已尽量通用）；
  ④ 首次把插件装进正在运行的 DSH；⑤ 从还没带这套机制的老版本升上来；
  ⑥ 移动端原生 / 桌面壳平台包的完整包更新（与插件外壳无关）。
  除这些之外，纯线路实现、移动 API、信封 / 鉴权、业务功能的更新都在代里换代，不重启 DSH。
- **回滚到不认识新注入来源的旧代时**，依赖注入的那部分会退化：总控上报的兜底信封里会缺第三方
  线路清单，也会缺局域网 / IPv6 / 直连 / TCP 这几类候选地址。这是有界的降级，只在「装坏了回滚」
  这种失败路径上出现，手机实时连接、心跳、二维码都不受影响（它们本来就住在代里）。
- **主链路 / 可选线路代码变化时**：该线路在「提交成功那一刻」短暂重连（DSH 不重启）；若这次更新
  自适应失败、回滚到旧代，则**旧实例一直活着、不会中断**（回滚只丢弃待建的新实例）。
- **主链路换成新实例时若新实例起不来**（例如端口被占）：保留 / 恢复旧实例继续跑、只记一条告警，
  这一拍不算切换成功——不会把没起来的实例当成当前（sidecar / 总控都如此）。
- **升级到启用本机制的版本时**：外壳也变了，首次需要重启一次 DSH；重启前新代在旧外壳下运行，
  主链路/可选线路可能短暂降级（按面板的重启提示重启即可恢复）。
- **回滚到比「启用本机制的版本」更旧的代时**：新外壳给的是稳定门面 + adopt，旧代按老契约把它当
  lifecycle 直接用，可能起不来。这种「退回更旧代」的路径需要重启一次 DSH 才恢复；只在更新失败且
  要回退到更旧代的少见情况出现。同为旧代时，boot 回退也接了 swap.abort，会先收回半途建出的实例。
- 真机（桌面三平台 × 手机双端 × 各线路）行为按项目规矩由用户点名验证，见
  `docs/update-continuity-device-checklist.md` 的清单。
