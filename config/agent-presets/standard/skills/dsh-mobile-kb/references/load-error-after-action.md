# 动作成功了却弹「加载失败」（请求超时 GET /sessions）

归档、改名、取消归档这类动作做完，目标那一行确实按操作变了（归档的没了、改名的变了），屏幕却马上弹一张「加载失败 · 请求超时（GET /sessions）」或干脆一句「请求超时」。这不是动作失败，也不是数据丢了——是动作成功之后那次**后台对账**的读列表请求，正好撞上这一刻连不上。

## 先认清症状

- 关键特征：**用户要做的动作已经生效**（去侧栏看，被归档的那条确实没了、没回来；改名的确实是新名字）。
- 报错是 `GET /sessions`（读列表）这种**对账读**，不是动作请求本身；带诊断时常见同一小段时间里 `tunnel-unavailable`（503，给不出隧道地址）或零星超时。
- 过一会儿 / 重连之后就恢复了，动作没有回滚。符合这几条就是本次的误报，不用重做动作。

## 怎么和真故障分开

- 若会话/工作区**一直读不出来**、报 `apiProxy 未注入` 或 `这台电脑没有注册 session/list` → 那是电脑端移动插件没装载，走 `references/plugin-not-loaded.md`，别当成这里。
- 若失败集中在某一精确时刻、还有 HTTP 522 或多接口连续超时 → 那是中转侧连不上电脑，走 `references/relay.md`。
- 这里说的是：动作已经成功、只是**动作后那一次读列表**超时，且很快自愈。

## 稳定处理口径

1. 先让用户确认那条操作是不是真的生效了（归档的没回来、改名的是新名）。生效了就直接告诉他：动作成功、不用重做，也不会丢数据。
2. 说明这是弱网或中转抖动下一瞬间没对上，App 会自动重试补上，等几秒或重连即可，不必反复点、不必重装。
3. 反复出现就按连接问题往下查（换网对比、看电脑是否在线、电脑插件是否启用），别停在“归档坏了”上吓用户。
4. 版本相关：新版 App 已不再为这类后台对账的短暂连接失败弹这个框，老版本才会遇到。给用户回的时候按“不影响已归档/已改结果”说，不承诺“已修好”。

## 边界

- 排查侧不改代码、不替用户重启或重装；只做识别与安抚，真要动手的是用户或维护者。
- 别把这条误报说成“归档失败/记录丢失”——那是把一次无害的读超时说成数据事故。
